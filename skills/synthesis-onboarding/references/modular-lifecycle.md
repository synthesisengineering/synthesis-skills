# Modular adoption and lifecycle

Use `synthesis setup --profile modular --skill synthesis-writing-craft --clients claude,codex` to expose one skill. Repeat `--skill` for additional roots. The resolver validates every declared dependency and rejects missing skills and cycles before writing client roots. Declared dependencies are exposed as skills; executable sibling support stays outside discovery. Scripts retain their canonical relative layout and are verified in physically isolated fixtures.

Only the selected skill directories receive discovery links under `~/.claude/skills` and `~/.agents/skills`. No settings, hooks, native plugin registration, service or workspace is enabled. The installer records exact payload file membership, hashes, modes, source identity and each owned link. A foreign file, directory or changed link blocks reconciliation and remains intact.

Default staging retains the complete verified release outside client discovery roots. This consumes download and disk space but adds no hooks, model calls or automatically loaded instructions. `--no-dormant-core` selects only required skill and executable support bytes; package acquisition projects the verified source before persisting it. Changing an existing opt-out to default staging reacquires the complete selected release before reporting optional assets as staged. Existing caches owned or used by earlier selections remain intact. Opting out does not grant deletion authority over those earlier files.

Standalone tool setup can explicitly call `synthesis stage-core --for-tool slopcheck`, `console` or `ownwords`. Its `--no-dormant-core` flag declines the optional core. The installed source CLI records that choice; the thin standalone launcher returns the declined result without acquisition or state writes. Staging writes a per-tool receipt and optional verified payload, without changing the active profile, CLI activation pointer or any client registration. Normal tool invocation and package postinstall do not silently install the ecosystem. A released staged payload carries its source descriptor for verified reuse during activation; an untagged development payload does not claim release provenance.

`activate --profile full` runs the existing full setup engine, including its normal user answers and client checks. `activate --profile skills-only` enables the complete catalog and its native lifecycle integration. Optional `--answers` and `--no-services` retain their ordinary setup meanings. Modular discovery links are suspended before native integration begins; the saved selection and payload remain. Full setup creates only the same layers offered by the existing reconciler.

`deactivate` removes the broader integration through its ownership-aware engine and restores the saved modular selection, or returns a standalone-tool activation to its disabled state. It stops registrations that the activation created and restores the prior global Git hook setting when this installer changed it. Preexisting independently owned registrations and shared runtime code remain. Edited registrations block removal instead of being overwritten. User repositories, personal source files and retained work are preserved.

`status` and `doctor` separate the six lifecycle planes. For modular selections, local desired/resolved/installed/source evidence can be verified while `live-loaded` remains `not-observed` and outcomes remain `not-requested`. Source provenance is independently re-derived from committed source or the verified active release, and the selection, payload and desired state must match a committed transaction. Invented source records or changed source bytes cannot establish a local PASS. A local PASS does not assert that a native client loaded the skill. A disabled selection reports installed removal and no expected live load. `repair` restores missing owned discovery links and rechecks payload integrity; changed foreign links or immutable payload drift require explicit reconciliation. `update` uses the same selected profile and staging choice while following its declared release policy. Neither runs unattended.

Modular changes participate in the existing locked transaction engine. A binding journal records before/after links and the exact transaction ID. After an operation finishes, its complete prepared commit is saved before desired state changes. A crash at that boundary finalizes the completed transition only when the desired-state alternatives, generation, receipt, payload and bindings still match; completed engine changes remain intact. An earlier interrupted broader operation requires verified engine rollback before restoring modular links and retiring its recovery obligation. Concurrent edits preserve the journal and fail closed. A journal left after a committed transaction is finalized only when committed desired state, receipt, payload and bindings still match. Journals and immutable payload evidence are retained. Recovery never creates native receipts or publication authority.
